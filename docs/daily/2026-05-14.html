Databricks high-performance rate limiting: sharded in-memory counters + async batch-reporting cut tail latency 10×
Databricks rebuilt its rate limiter from Redis-backed synchronous checks (10–20ms P99 due to two network hops) to a three-layer architecture: Dicer-routed sharded in-memory counters eliminating Redis, then client-side batch-reporting where clients make zero synchronous calls on the hot path and instead report counts every ~100ms asynchronously. The inversion — the rate limiter is told after decisions rather than consulted before — accepts ~5% overshoot in exchange for ~10× tail latency reduction and predictable server load; token bucket replaced fixed-window counting once the in-memory state layer was stable.

Cloudflare post-mortem: Linux kernel idle-time optimisation caused QUIC CUBIC congestion window death spiral
A Linux kernel optimisation for idle periods inadvertently triggered a QUIC death spiral in Cloudflare's quiche CUBIC implementation: the congestion window got stuck at minimum because idle time was measured from last packet sent rather than last ACK received. Fix: measure idle from the most recent acknowledgement, allowing the controller to distinguish true idleness from congestion — a subtle but critical distinction for any team running QUIC at scale.
